## 2. ERD에서 바꾼 것과 이유

### ① USERS를 두 개로 나눔
- RLS는 **행 단위**라서, 한 행 안에서 "닉네임은 공개, 키·출생연도는 비공개"를 못 나눔.
- `users`: 닉네임, 역할, 온보딩 단계 → 로그인한 사람 누구나 읽기 (커뮤니티에 필요)
- `user_health`: 가입 이름, 출생연도, 키, 시작·목표 체중, 단백질 목표 → 본인만
- 회원가입 시 트리거가 두 행을 자동으로 만듦

### ② MEALS를 기록 + 음식으로 나눔
- ERD는 `meals` 한 행 = 음식 1개(`food_id`, `portion`)였음.
- 지금 화면은 "점심 한 끼에 음식 여러 개"임. 그래서 `meals`(한 끼) + `meal_items`(음식)로 나눔.
- `meal_items`는 저장할 때의 이름·영양을 **스냅숏**으로 보관. 음식 DB가 바뀌어도 옛 기록은 그대로임.
- 탄·단·지가 `null`이면 화면의 "정보 없음"으로 연결됨.

### ③ PREDICTIONS를 멀티라벨에 맞춤
- ERD: `meal_id` UNIQUE, `top3`, `confidence` → 사진 1장에 결과 1개라는 전제였음.
- 변경: 사진 1장 → 라벨 여러 줄. 라벨마다 `score`(내부용), `threshold`, `status`(인식 결과/확인 필요), `mode`(model/mock)를 둠.
- 사용자가 **뺀 라벨도 남김** (`user_action = 'excluded'`) → 나중에 모델이 어디서 틀리는지 분석할 때 씀.
- 사용자는 피드백 칸(`user_action`, `corrected_food_id`)만 고칠 수 있음. 점수는 못 건드림.

### ④ FOODS에 "내 음식" 합침
- `owner_id`가 `null`이면 공용 음식(식약처 DB 등), 있으면 내가 등록한 음식.
- 남이 등록한 음식은 안 보임.

### ⑤ 그 외
- `body_logs.is_baseline`: 온보딩 최초 체중은 사람당 1개만 (부분 UNIQUE)
- `intake_logs`: 물은 mL 필수, 영양제·약은 항목 연결. `daily_checks.water_cups`는 옛 기록용으로 남김
- `model_versions`: 성능 칸은 **실측값만** 넣고, 없으면 `null`
- 닉네임: 대소문자만 달라도 중복 처리

## 3. 누가 무엇을 쓸 수 있나 (RLS)

| 데이터 | 앱(사용자)이 직접 | FastAPI(서버)만 |
|---|---|---|
| 프로필 닉네임·온보딩 | 본인 수정 (**role은 못 바꿈**) | |
| 건강 정보, 섭취, 하루 체크, 식단 | 본인 읽기·쓰기 | |
| 투약·증상·체성분 | 본인 읽기·삭제, **민감정보 동의가 있어야** 쓰기 | |
| 내 음식 | 본인 추가·수정·삭제 | 공용 음식 등록 |
| 사진 인식 결과 | 본인 읽기 + 피드백만 | 결과 저장 |
| 게시글·댓글 | 읽기 (보이는 글 + 내 글) | 작성·수정·삭제 (**안전 검사 후**) |
| 좋아요·신고 | 본인 추가·취소 | |
| 필터 로그·관리자 조치 | 관리자만 읽기 | 기록 |
| 식단 사진 (Storage) | 본인 폴더 읽기·삭제 | 업로드 (**EXIF 제거 후**) |

- 게시글을 서버만 쓰게 한 이유: 앱에서 직접 넣으면 금칙어 검사(판매·양도 등)를 건너뛸 수 있어서.
- 계획서의 "RLS + 서버 권한 확인 이중 적용"을 이렇게 구현함.

### 동의 철회와 탈퇴
- 민감정보 동의 철회 → `withdraw_health_consent()` 실행 → 투약·증상·체성분 즉시 삭제. 식단은 남음.
- 동의 이력은 지우지 않고 `withdrawn_at`만 찍음.
- 탈퇴(`auth.users` 삭제) → 연결된 모든 데이터 자동 삭제 (cascade).

## 4. 검증 결과 (로컬, 실제 Supabase 아님)

PostgreSQL 16에 Supabase 흉내 환경(auth, storage, 역할)을 만들고 적용했다.

- 스키마 적용: 테이블 22개, 에러 없음
- RLS·제약 테스트: **32개 통과 / 실패 0**

확인한 것:
- 동의 없이 투약 기록하면 막힘, 동의하면 저장됨, 철회하면 삭제되고 다시 막힘
- B는 A의 투약·체중·식단·인식 결과·내 음식·사진·건강 정보를 못 봄. 닉네임은 보임
- B가 A의 기록을 고치거나 지우려 해도 바뀌는 게 없음. A의 식사에 음식을 끼워넣는 것도 막힘
- 내 role을 admin으로 바꾸기, 게시글 직접 작성, 인식 점수 조작 → 막힘
- 최초 체중 2번 저장, 미래 시각, 체지방률 범위 밖, 사진 없는 사진 기록, mL 없는 물 기록 → 막힘
- 탈퇴하면 데이터 전부 삭제

다시 돌리기: `PGUSER=postgres bash docs/db/test/run_local.sh`

**한계:** 진짜 Supabase가 아니라 흉내 환경임. 실제 프로젝트에 적용한 뒤 한 번 더 돌려봐야 함.

## 5. 정해야 할 것 (승인 요청)

1. **테이블 4개 추가** (18 → 22) 괜찮은지 → 계획서 ERD 그림도 갱신 필요
2. **게시글 작성은 서버만** 하는 방식 괜찮은지 (대안: DB 함수 안에서 금칙어 검사)
3. **동의 철회 시 식단은 남기기** 괜찮은지 (식단은 민감정보로 안 봄)
4. **로그인 수단**: 카카오·구글·애플은 Supabase 기본 지원, 네이버는 따로 개발 필요 → 1차는 카카오+구글 추천
5. **무료 플랜 일시정지**(7일 미사용) 대비: 발표 전 Pro 전환 여부

## 6. 승인 후 순서 (제안)
1. Supabase 프로젝트 생성 (서울 리전)
2. `supabase/migrations/`에 이 SQL을 첫 마이그레이션으로 넣고 적용
3. 실제 프로젝트에서 RLS 테스트 다시 실행
4. 음식 DB 초기 데이터 넣기 (목업 56종 → 식약처 DB 값으로 교체, 출처 기록)
5. 프론트를 화면 하나씩 목업 → Supabase로 전환 (온보딩 → 체중 → 투약 → 식단 → 커뮤니티 순)
