### 식단에 건강정보가 섞이는 경우 (검토 결과)
- 지금 식단 테이블에는 **메모 칸이 없다.** 그래서 "속이 안 좋아서 조금만 먹음" 같은 증상 글이 식단에 들어갈 자리가 없다. 증상은 `symptoms`로만 저장된다.
- 사진 인식 결과(`predictions`)에는 음식 이름과 점수만 있다.
- 사진 파일은 서버가 EXIF(촬영 위치·기기 정보)를 지우고 저장한다 (`photo_exif_stripped = true` 필수).
- **나중에 식단 메모를 추가한다면** 그 칸은 민감정보로 분류해서, 철회할 때 비우는 대상에 넣어야 한다.

### 프론트 문구와 맞출 것 (승인 필요)
- 지금 가입 동의 화면의 민감정보 항목에는 "수집 항목: 투약 기록, 증상·컨디션, 체중·체성분, **식단**"이라고 적혀 있다.
- 결정 3번(식단 유지)과 어긋나므로, 문구에서 **식단을 빼고** 키·복용약을 넣는 게 맞다.
- 바꿀 문구 예시: "투약 기록, 증상·수면·식욕·컨디션, 키·체중·체성분, 복용약"
- 화면 수정은 승인 후 진행한다.

## 3. 처리 방식

### 동의 철회: `withdraw_sensitive_consent()` (DB 함수, 본인만 호출)
1. `consents`에서 sensitive 동의에 `withdrawn_at` 기록
2. 2번 표의 "삭제" 대상 행 삭제
3. 2번 표의 "비움" 대상 컬럼 null 처리, 빈 `daily_checks` 행 삭제
4. 테이블별 처리 건수를 JSON으로 돌려줌 → 화면에 "투약 12건, 체중 30건을 지웠어요"처럼 표시 가능

- 전체가 한 트랜잭션이라 중간에 실패하면 아무것도 안 지워짐
- 철회 후에는 민감정보 쓰기가 RLS로 막힘. 다시 동의하면 새 동의 행이 생기고 다시 쓸 수 있음

### 탈퇴: 서버 API (`DELETE /me`)
1. Storage `meal-photos/{user_id}/` 폴더 파일 전부 삭제 (Storage API)
2. Supabase Auth 사용자 삭제 → 모든 테이블 행이 cascade로 삭제
3. 순서를 지키는 이유: DB부터 지우면 사진 파일이 주인 없이 남음

### 사진 기록 삭제: 서버 API (`DELETE /meals/{id}`)
- 앱은 사진 기록을 직접 못 지운다 (RLS). 서버가 Storage 파일 → DB 행 순서로 지운다.
- 수동 기록(사진 없음)은 앱이 직접 지울 수 있다.
