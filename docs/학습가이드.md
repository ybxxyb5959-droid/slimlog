# SlimLog 학습 가이드 — 구조 이해부터 재구현까지

1차 완성본 코드를 읽고, 같은 걸 처음부터 다시 만들 수 있게 정리한 문서다.
각 절 끝의 "직접 해 보기"를 순서대로 따라 하면 된다.

---

## 1. 전체 구조 (한 장 요약)

```
[브라우저: React 앱]
   │  ① 로그인(카카오·구글) ── Supabase Auth ── JWT(로그인 증표) 발급
   │  ② 일반 기록 읽기·쓰기 ── Supabase DB (RLS 가 "내 행만" 막아 줌)
   │  ③ 검사·계산·파일·추론 ── FastAPI 서버 (JWT 를 확인하고 service_role 로 DB/Storage 접근)
   │  ④ 눈바디 사진 ────────── 이 기기 IndexedDB (암호화, 서버로 안 감)
   │  ⑤ 인바디 결과지 ──────── 기기 안에서 글자 인식 → 숫자만 서버로
   ▼
[Supabase] Postgres(22 테이블 + RLS) · Auth · Storage(meal-photos, 비공개)
[FastAPI ] /posts(금칙어) /admin/actions /meals/photo(EXIF 제거·인식) /body-logs/ocr /residual-curve /me(탈퇴)
[AI 학습 ] 사용자 PC 에서 EfficientNet-B0 멀티라벨 → ONNX → 서버 models/
```

**왜 이렇게 나눴나**
- 앱이 바로 DB 에 쓰면 빠르고 코드가 적다. 대신 "남의 데이터"는 RLS 로 DB 가 직접 막는다.
- 앱에 맡기면 안 되는 일만 서버로 보낸다.
  - 금칙어 검사: 앱에서 하면 건너뛸 수 있다
  - 관리자 권한: 화면에서 속일 수 있다
  - 사진 EXIF 제거: 원본에 위치정보가 들어 있다
  - 파일 삭제 순서: 파일과 DB 를 함께 지워야 한다

## 2. 프론트엔드 (`src/`)

| 폴더 | 역할 |
|---|---|
| `app/router.tsx` | 주소 ↔ 화면. `LiveGate` 로 로그인·동의·온보딩 출입 관리 |
| `features/*` | 화면 (기능별 폴더). 화면은 데이터를 직접 안 부르고 `services`·`stores` 만 쓴다 |
| `services/*` | 데이터 접근. **목업/실서비스 모드 분기**가 여기 모여 있다 |
| `services/live/*` | Supabase 쿼리 (테이블별 함수) |
| `stores/*` | zustand 화면 캐시. 실서비스는 로그인 때 DB 에서 채우고, 저장 성공 후 갱신 |
| `lib/supabase.ts` | 클라이언트 + `isLive` (환경변수가 있으면 실서비스) |
| `lib/api.ts` | FastAPI 호출 (토큰 첨부, `{code,message,field}` 오류) |
| `lib/eyebodyVault.ts` | 눈바디 암호화 금고 |
| `lib/inbodyParser.ts` | OCR 글자 → 숫자 |
| `lib/pk/residual.ts` | 참고 곡선 계산 (서버 `app/pk.py` 와 같은 식) |

**저장 패턴 2가지** (코드 읽을 때 이것만 알면 됨)
1. **기다렸다가 반영**: 투약·체중·증상
   - `await insert…()` 성공 → 스토어 갱신 → 토스트
   - 실패하면 화면이 안 바뀌고 오류 토스트
2. **먼저 반영, 실패 시 되돌림**: 섭취·식단·좋아요
   - 화면을 바로 바꾸고 → 뒤에서 저장 → 실패하면 이전 상태로 되돌리고 토스트
   - 반응이 빨라야 하는 곳에 씀

**직접 해 보기**: `services/body.ts` 의 `addBody` 를 따라가서 `services/live/records.ts` → Supabase → `stores/recordsStore.ts` 순서를 그려 보기.

## 3. DB · RLS (`supabase/`)

- 테이블 22개: `docs/db/ERD_v2.2_22tables.png`, 설명은 `docs/DB_Supabase_설계안.md`
- 마이그레이션 6개: `supabase/migrations/` (번호 순서대로 적용)
- RLS 핵심 식
  - `using (user_id = auth.uid())` → 내 행만 읽기
  - `with check (user_id = auth.uid() and has_consent('sensitive'))` → 동의해야 쓰기
- 컬럼 단위 권한: `revoke update … ; grant update (nickname, …)` → role 같은 칸은 못 바꿈
- 테스트
  - `supabase/tests/rls_test.sql` (46개): 역할을 바꿔 가며 실제로 막히는지 확인
  - `integration.mjs` (30개): HTTP 로 Auth·Storage 확인

**직접 해 보기**: `rls_test.sql` 의 테스트 하나를 골라 정책을 일부러 지워 보고 FAIL 이 나는지 확인 (로컬에서만).

## 4. 인증 · 권한 흐름

1. `/login` → `signInWithOAuth('kakao')` → 카카오 로그인 → `/auth/callback?code=…`
2. supabase-js 가 code 를 세션으로 교환 (PKCE) → `authStore` 가 `users`·`user_health`·`consents` 를 불러옴
3. `LiveGate`
   - 필수 동의 없음 → `/consent`
   - 온보딩 미완료 → `/onboarding`
   - 둘 다 됐으면 → 앱 화면
4. 서버 호출: `Authorization: Bearer <access_token>`
   - 서버는 HS256(비밀키) 또는 JWKS(공개키)로 서명 확인
5. 관리자: 토큰이 아니라 **DB 의 `users.role`** 을 매번 확인. 앱은 role 칸을 못 바꾼다

## 5. FastAPI (`server/`)

- 엔드포인트 표: `server/README.md`
- 파일 구성
  - `auth.py`: 토큰 확인 · 관리자 확인
  - `db.py`: service_role 로 REST·Storage·Auth Admin 호출
  - `safety.py`: 금칙어 (프론트와 같은 규칙)
  - `images.py`: 사진 정리 (디코딩 확인 → EXIF 제거 → 1600px JPEG)
  - `recognizer.py`: ONNX 추론. 모델이 없으면 목업 (`mode` 저장)
  - `routers/*`: 기능별 API
- **service_role 은 RLS 를 우회한다.** 그래서 모든 엔드포인트가 `user.id` 로 소유권을 직접 확인한다 (예: `_owned()`).
- 테스트: `server/tests/` (14개). 실제 로컬 Supabase 토큰으로 호출하고 DB 결과까지 확인

**직접 해 보기**: `/posts` 에 새 금칙어 규칙을 추가하고 `safety.py` 와 `src/lib/communitySafety.ts` 둘 다 고친 뒤 테스트 추가.

## 6. 음식 AI (`ai/`)

- 0단계: `ai/scripts/inspect_labels.py` — 라벨 품질과 멀티라벨 비율 실측
- 1단계: `ai/train/README.md` — 데이터 분할 → 실험 A/B/C → val 로 기준값 → test 1회 → ONNX
- 서버 연결: `server/models/food_multilabel.onnx` + `.json` 을 두면 `model_status: ready`
- 화면: "인식 결과 / 확인 필요"만 보여 주고 점수는 `predictions` 에 내부 저장
- 사용자가 고친 결과(`user_action`)는 `photo_improve` 동의자만 모델 점검에 쓴다 (`model_feedback` 뷰)

## 7. 인바디 OCR

- 결과지 사진 → 브라우저 Tesseract.js(kor+eng) → `parseInbody()` → 확인·수정 폼 → 서버 `/body-logs/ocr`
- 서버가 다시 검사한다
  - 범위·교차 검증
  - 민감정보 동의
  - 10분·0.1kg 중복 → 409
- 통과하면 `BODY_LOG_SOURCES` 에 출처를 남긴다
- 한계: 결과지 양식마다 글자 배치가 다르다. 지원할 1종 샘플로 파서를 맞춰야 한다

## 8. 보안 체크리스트

| 위협 | 막는 곳 |
|---|---|
| 남의 기록 읽기·쓰기 | RLS (DB) + 서버 소유권 확인 |
| 관리자 권한 상승 | role 칸 수정 권한 없음 + 서버가 DB role 재확인 |
| 금칙어 우회 | 게시글 쓰기 권한을 앱에서 제거 (서버만) |
| 사진 위치정보 노출 | 서버 재인코딩(EXIF 제거), 눈바디는 캔버스 재저장 |
| 사진 무단 접근 | 비공개 버킷 + 본인 폴더만 + 10분 서명 URL |
| 서버 키 노출 | service_role 은 서버 환경변수에만. `.env*` 는 git 제외 |
| 민감정보 동의 없는 저장 | RLS `has_consent('sensitive')` + 서버 OCR 저장도 확인 |
| 탈퇴 후 파일 잔존 | 서버가 Storage → Auth 순서로 삭제 |

## 10. 기술 선택 이유

| 선택 | 이유 | 대안과 비교 |
|---|---|---|
| React + Vite + TS | 화면이 많고 상태가 복잡 → 타입으로 실수 줄이기 | Next.js: 서버 렌더링이 필요 없는 앱이라 과함 |
| zustand | 가벼운 전역 상태, 코드 적음 | Redux: 이 규모엔 보일러플레이트가 많음 |
| Supabase | 인증·DB·파일·RLS 한 번에 | MySQL+직접 구현: 로그인·권한·파일을 다 만들어야 함 |
| FastAPI | 모델과 같은 파이썬, 타입 검증(pydantic) | Node 서버: AI 추론 코드와 언어가 갈림 |
| EfficientNet-B0 | CPU 에서도 빠르고 전이학습 성능이 좋음 | YOLO: 박스 라벨·학습 비용 큼, 영역 그리기 없앤 방향과 안 맞음 |
| ONNX Runtime | 서버에 PyTorch 없이 가볍게 추론 | |
| Tesseract.js | 결과지 사진을 기기 밖으로 안 보내고 OCR | 클라우드 OCR: 건강 서류 업로드 필요 |

## 11. 처음부터 다시 만드는 로드맵 (추천 순서)

1. **화면만 (1주)**: Vite+React+TS, 라우터, 홈·기록 화면 3개, 목업 데이터
2. **Supabase 기초 (1주)**
   - 테이블 3개(users, doses, body_logs)
   - RLS `user_id = auth.uid()`
   - 이메일 로그인
3. **CRUD 연결 (1주)**: 투약 추가·수정·삭제, 새로고침 유지, 두 계정으로 데이터 분리 확인
4. **동의·민감정보 (0.5주)**: consents + `has_consent` 정책 + 철회 함수
5. **FastAPI (1주)**
   - `/health`
   - JWT 확인
   - `/posts` 금칙어
   - pytest 로 "남의 글 수정 403" 확인
6. **파일 (0.5주)**: 비공개 버킷, 서버 업로드(EXIF 제거), 서명 URL
7. **AI (2주+)**
   - 라벨 점검 → 작은 데이터로 학습 A → 지표 읽기
   - 학습 B → ONNX → 서버 연결
8. **OCR·눈바디 (1주)**: Tesseract.js, Web Crypto(AES-GCM) + IndexedDB
9. **테스트·배포 (1주)**: Playwright E2E, 배포, 운영 확인

막히면 이 저장소의 같은 기능 파일을 열어 비교한다. 파일 이름이 기능 이름과 같다.
